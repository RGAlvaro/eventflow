### 2026-10-09 — Receptor controlado del hito 4 (P-11)

- **Cambio y motivo:** se cerró P-11 y se añadió un servicio receptor independiente, preparado para publicarse mediante un proxy HTTPS en un host externo. Tiene cuatro rutas de escenario preconfiguradas: éxito inmediato, dos respuestas 503 antes del éxito, una respuesta 429 con `Retry-After`, y fallo persistente de la generación inicial hasta que un replay autorizado crea la generación 2. No existe una ruta pública para cambiar el destino o el modo. El dominio, certificado y proveedor concretos se fijarán en P-08, antes de desplegarlo.
- **Firma y aislamiento:** cada ruta usa el secreto de firma de su endpoint, recibido una sola vez desde la API de gestión y guardado en un archivo privado fuera de Git. El receptor recalcula el código de autenticación HMAC sobre el timestamp y los bytes exactos del cuerpo; compara el resultado sin depender del tiempo que tarde la comparación en diferenciar caracteres. Solo después comprueba que los IDs y la generación de las cabeceras coinciden con el JSON firmado. Una fecha fuera de cinco minutos o una versión de secreto vencida se rechaza. El servicio se dedica a una organización de demo; su consulta de resultados usa un segundo token reservado al backend, que deberá verificar el tenant antes de mostrarlos al navegador. EventFlow seguirá validando el DNS y la IP pública en cada envío; el receptor no introduce una excepción SSRF de producción.
- **Persistencia y duplicados:** SQLite conserva por ruta, entrega y generación el número de peticiones, último código, hora y marca de procesado, sin payload, firma, secreto ni cuerpo de respuesta. Una transacción `BEGIN IMMEDIATE` serializa escrituras: si dos solicitudes válidas llegan a la vez, solo una pasa de no procesada a procesada. Cuando ya existe un 200, las copias físicas reciben 200 sin volver a procesarse; un replay tiene una generación distinta y puede procesarse. El archivo SQLite y su directorio se crean o validan con permisos `0600` y `0700`. Las operaciones SQLite se trasladan a un hilo para no bloquear el bucle HTTP mientras esperan el disco.
- **Verificación observada:** con PostgreSQL y Redis locales, `pytest -ra` terminó con **61 pruebas pasadas y ninguna omitida**. La nueva prueba de integración arrancó el receptor HTTP real, reclamó entregas desde PostgreSQL, envió webhooks firmados y comprobó tanto 503→503→200 como siete 503→`dead_lettered`→replay autorizado→200. Otras pruebas cubrieron manipulación del cuerpo, fecha, rutas/secretos distintos, solapamiento y vencimiento de versiones, tamaño, 429, concurrencia, reinicio, observación privada y permisos de archivos. `alembic check` no detectó operaciones nuevas; `ruff check .`, `ruff format --check .`, `mypy` y `git diff --check` pasaron. El primer ensayo de suite falló porque la base local seguía en una migración antigua; tras aplicar `alembic upgrade head` y fijar la URL de Redis, pasó completa. Esta evidencia es local y no demuestra todavía TLS/DNS en un host externo.
- **Cierre del corte:** la PR #11 pasó sus dos checks de GitHub Actions y se fusionó en `feat/hito4-observability-api` con commit `182dbb6`; la rama local se sincronizó mediante `git pull --ff-only`. La PR #10 del hito 4 sigue abierta porque el receptor todavía no está conectado a la UI.

### 2026-10-08 — Sesión del operador del hito 4 (P-10)

- **Cambio y motivo:** se añadió una identidad de operador distinta de las claves API. Un comando ejecutado en el servidor crea una contraseña aleatoria que muestra una vez, guarda su hash con `scrypt` y permite rotarla o deshabilitar el usuario. `scrypt` usa una sal distinta por contraseña y requiere memoria además de tiempo para dificultar pruebas masivas de contraseñas robadas. El navegador nunca recibe la clave `manage`: al iniciar sesión obtiene un token aleatorio en una cookie `HttpOnly`, mientras PostgreSQL conserva solo su hash, organización, usuario, vencimiento y estado de revocación. Una cookie de sesión evita guardar credenciales de gestión en el JavaScript del navegador.
- **Procedimiento y criterio:** P-10 fija ocho horas de duración absoluta, una sesión activa por operador y `SameSite=Strict`; producción añade `Secure`. Las mutaciones con cookie requieren otra cookie legible y el mismo valor en `X-CSRF-Token`, cuyo hash se liga a la sesión en PostgreSQL. CSRF es una petición que otro sitio intenta hacer con las cookies del navegador; el encabezado adicional demuestra que la aplicación del mismo origen pudo leer el token. Las peticiones con `Authorization` siguen validando solo la clave API, sin caer a una cookie si la cabecera es incorrecta. La auditoría de gestión y replay registra el ID del operador o de la clave, con restricción de base que impide asignar dos actores a un replay. Redis limita intentos por usuario y en conjunto; la revisión detectó que solo limitar por usuario permite eludir el control probando muchos nombres distintos, y añadió el segundo bucket con una prueba específica. El bloqueo de filas de operador antes de sesión conserva el mismo orden durante login, mutaciones y logout, evitando una espera circular con la rotación de contraseña.
- **Verificación observada:** la PR draft #10 ejecutó CI 37747354959 con PostgreSQL y Redis reales: migración 0008, `alembic check`, **49 pruebas pasadas y ninguna omitida**, Ruff, formato y mypy. Las pruebas HTTP comprobaron cookie `HttpOnly`/`Secure`/`SameSite`, contraseña incorrecta, lectura y replay tenant, CSRF ausente, erróneo o de sesión anterior, prioridad de `Authorization`, auditoría del operador, reemplazo, logout, rotación, expiración, deshabilitación, caída de Redis y límites por usuario y global. En local, `pytest -ra` fuera del sandbox pasó 22 pruebas y omitió 27 por falta de PostgreSQL/Redis; las pruebas de integración se verificaron en CI. La revisión de fiabilidad examinó tenant, revocación concurrente, fuga de claves y trabajo de contraseña; el bypass por nombres distintos se corrigió. No se verificó aún un navegador real detrás del proxy HTTPS del VPS.

### 2026-10-07 — Gestión tenant, admisión y retención del hito 3

- **Cambio y motivo:** se completó el corte de seguridad y límites en la PR #8. La primera organización y su clave `manage` se crean con un comando de operador conforme a D-15; la API posterior emite claves `publish` o `manage`, permite revocarlas y gestiona endpoints, suscripciones, secretos de firma y replay. Una clave bruta se muestra solo en su creación y PostgreSQL guarda su hash; los secretos de firma se guardan cifrados. Cada operación busca el recurso por su ID **y** por la organización de la credencial. Este segundo filtro impide que conocer un UUID de otro tenant otorgue acceso.
- **Procedimiento y criterio:** PostgreSQL bloquea la fila de organización durante la comprobación de cuotas y la creación de eventos o recursos. Ese bloqueo serializa peticiones simultáneas del mismo tenant: ambas ven el resultado de la anterior y no pueden superar juntas la cuota diaria, el número de destinos ni la capacidad de entregas pendientes. Redis ejecuta el *token bucket* mediante un script atómico y su reloj; el bucket limita ráfagas entre varias API, mientras PostgreSQL sigue siendo la fuente de verdad de lo aceptado. Si Redis falla, la API responde `503` antes de insertar trabajo. La rotación del secreto crea una versión pendiente, permite instalarla en el receptor y después la activa; la versión anterior permanece descifrable durante 24 horas para comprobar envíos ya iniciados. Un comando recifra todas las versiones con una nueva clave maestra antes de retirar la antigua. La purga usa `terminal_at`, fijado cuando todas las entregas terminan; vuelve a comprobar el estado bajo bloqueo antes de borrar el agregado, y replay borra ese reloj para reiniciar el plazo.

### 2026-10-07 — Inicio del hito 3: secretos webhook cifrados

- **Cambio y motivo:** se creó `feat/hito3-backend-security` desde `main` actualizado y el corte trazable en `docs/work/hito3-backend-security/`. El worker anterior usaba como secreto HMAC los bytes de la columna llamada `signing_secret_ciphertext`; el nombre daba una impresión de cifrado que el comportamiento no cumplía. Se añadió AES-256-GCM, un cifrado autenticado que oculta el secreto y rechaza modificaciones al verificar una etiqueta criptográfica. Los IDs de organización y endpoint y la versión entran como datos asociados: no se cifran, pero quedan ligados a la autenticidad del texto cifrado, de modo que copiarlo a otra fila no produce un secreto válido.
- **Procedimiento y criterio:** la migración 0004 agrega identificador de clave y versión, cifra filas previas dentro de la transacción y exige la clave maestra si hay filas que convertir. Si falta la clave o el texto cifrado está alterado, el reclamo del worker se revierte antes de registrar un nuevo intento; el reconciliador puede volver a anunciar la entrega tras restaurar la clave. El webhook emite `X-EventFlow-Key-Id` para que un receptor pueda elegir el secreto correcto durante una futura rotación. La dependencia `cryptography` quedó fijada en `uv.lock`; la API y el worker reciben la misma configuración de claves en Compose. Aún no se creó la API de gestión ni el mecanismo de rotación.
- **Verificación observada:** `ruff check .`, `ruff format --check .`, `mypy` y `git diff --check` pasaron. La suite local fuera del sandbox pasó **19 pruebas** y omitió **16** por falta de PostgreSQL/Redis en esta sesión WSL. La prueba nueva crea una base aislada en la versión 0003, inserta un secreto previo y verifica su cifrado y lectura tras 0004; otra comprueba que una clave ausente no consume intentos. ### 2026-10-05 — Primer recorrido de entrega con recuperación y firma

- **Cambio y motivo:** se añadieron despachador, worker Celery, reconciliador y emisor HTTPS al corte del hito 1. El *outbox* ya guardaba en la misma transacción que el evento una fila que representa el aviso por publicar. El despachador lee esa fila desde PostgreSQL, avisa a Celery mediante Redis y solo entonces marca la publicación. Si la conexión TCP con Redis es rechazada, la fila permanece pendiente; si la publicación se duplica, el reclamo de la entrega en PostgreSQL impide que dos avisos normales creen dos intentos a la vez. El reconciliador vuelve a anunciar entregas pendientes o con reserva vencida aunque el outbox figure publicado, para recuperar avisos perdidos o procesos muertos.
- **Procedimiento y criterio:** un *lease* es la reserva de una entrega durante 60 segundos, identificada por un token y calculada con el reloj de PostgreSQL. El worker confirma el reclamo y el intento antes de enviar HTTP, sin mantener abierta la transacción durante la red. Al recibir el resultado, solo el token aún vigente puede cambiar la entrega; un resultado tardío queda registrado en su intento sin pisar el estado nuevo. Un bloqueo transaccional de PostgreSQL serializa la comprobación de capacidad global, de cuatro envíos simultáneos, entre procesos. Cada tarea limita el envío completo a 20 segundos y Celery tiene límite duro de 30; el reconciliador revisa cada 10 segundos. Por ahora, un fallo se programa en PostgreSQL a 30 segundos y tras siete intentos va a `dead_lettered`; el hito 2 especializará respuestas, espera y límites por endpoint.
- **Seguridad de salida y firma:** antes de cada intento se analiza la URL, se resuelven sus direcciones IPv4 e IPv6 y se rechaza todo el destino si alguna no es pública. La conexión usa una IP validada y conserva el nombre original para `Host`, SNI y comprobación del certificado TLS. Se desactivan proxies de entorno y redirecciones. El cuerpo JSON se serializa una vez; la firma HMAC-SHA256 cubre el timestamp y esos bytes exactos, y el receptor de prueba comprueba firma, IDs y generación antes de responder 200. HTTP a loopback requiere una URL exacta y un entorno test o development configurado explícitamente; el entorno por defecto es production y lo rechaza. Los secretos de fixture aún se guardan sin cifrado recuperable: P-05 debe resolverse antes de exposición pública, al igual que las reglas de salida del VPS en P-08.

Se publicó un evento por `POST /api/v1/events` (`202`), el outbox produjo un aviso en Redis y un Celery real lo procesó hasta un receptor que verificó la firma antes de responder 200; otra prueba mató abruptamente un proceso con una entrega reclamada y la recuperó desde PostgreSQL sin nueva ingesta. ### 2026-10-05 — Decisión P-03 sobre seguridad de destinos webhook

- **Cambio y motivo:** se cerró el diseño P-03 en la rama activa del primer recorrido. Una petición web iniciada por el worker puede convertirse en *server-side request forgery* (SSRF) si una URL controlada por un usuario le hace contactar con servicios internos. Por ello, el primer corte aceptará en producción solo HTTPS a nombres DNS públicos por el puerto 443. Las URL por IP, otros puertos y HTTP público quedan fuera de este alcance; el receptor HTTP local se habilitará únicamente con configuración explícita de pruebas o desarrollo aislado.
- **Procedimiento y criterio:** antes de cada intento se resolverán las direcciones IPv4 (A) e IPv6 (AAAA) del nombre y se rechazará el destino si alguna no es pública. DNS es el servicio que traduce el nombre a una IP; una respuesta puede cambiar entre dos consultas. Para evitar que el cliente compruebe una IP y conecte a otra, HTTPX se dirigirá a una IP ya comprobada mientras conserva el nombre original en `Host` y en la identificación TLS (`sni_hostname`). TLS seguirá verificando el certificado para ese nombre. Se desactivarán redirecciones y proxies de entorno, que abrirían rutas de conexión distintas. En el VPS se añadirá una barrera de red que bloquee destinos internos no autorizados sin impedir las conexiones necesarias del worker a PostgreSQL, Redis y DNS. Se descartó validar solo al guardar la URL, resolver sin fijar la conexión o confiar únicamente en una lista de dominios: esas opciones no cierran la ventana de cambio DNS descrita por OWASP. Si no se demuestra la integración segura, el producto permanecerá limitado a destinos preconfigurados.
- **Verificación:** se cotejó la elección con `docs/architecture.md`, el contrato del primer corte, la guía SSRF de OWASP y la extensión `sni_hostname` de httpcore. Se comprobó que la rama activa estaba limpia y contenía `origin/main` después de actualizar referencias remotas; `git diff --check` pasó. La revisión de fiabilidad no encontró una ruta documental que permitiese conectarse a una IP sin validar, seguir una redirección o usar un proxy de entorno. Esta revisión valida la coherencia del diseño, no la seguridad de una conexión que aún no se ha implementado. No se ejecutaron pruebas funcionales de salida HTTP porque no existe todavía esa ruta.
- **Pendiente:** implementar y probar con conexión observable la resolución A/AAAA, una respuesta DNS que cambia, redirecciones, proxies de entorno, TLS y la IP efectiva de destino. ### 2026-10-02 — Decisión P-04 sobre recuperación del worker

- **Cambio y motivo:** se cerró el diseño P-04 para poder implementar el primer worker del hito 1. Un *lease* es una reserva temporal registrada en PostgreSQL: el worker recibe un token al reclamar una entrega y solo puede confirmar su resultado mientras conserve esa reserva. Se eligieron 60 segundos sin renovación inicial, con plazo total de envío HTTP de 20 segundos y límite duro de tarea de 30 segundos. El margen permite que una tarea normal termine antes de que otro worker reclame la entrega; si la implementación no consigue acotar todo el trabajo, habrá que revisar esos valores antes de enviar webhooks.
- **Procedimiento y criterio:** un reconciliador consultará PostgreSQL cada 10 segundos para recuperar entregas pendientes, reintentos debidos y reservas vencidas. Celery confirmará la tarea después de ejecutarla (`acks_late`), reservará como máximo un aviso por proceso (`prefetch_multiplier=1`) y usará visibilidad Redis de 300 segundos. Se mantienen la confirmación de tareas fallidas y la opción de reencolar por muerte del proceso desactivada. Esta última puede causar ciclos de caídas; además, Celery puede confirmar la tarea aunque muera el proceso hijo. Por ello, el reconciliador es el mecanismo de recuperación y los avisos duplicados deben resultar inocuos gracias al reclamo condicional de PostgreSQL. La planificación de reintentos permanece en la base, no en temporizadores de Celery.
- **Verificación:** se cotejó la decisión con las columnas `lease_token` y `lease_expires_at` existentes, el contrato de `docs/architecture.md`, el plan del corte y la documentación oficial de Celery sobre confirmación, pérdida de worker, prefetch y visibilidad Redis. Esta revisión respalda la coherencia del diseño; todavía no demuestra el comportamiento de un worker, porque aún no existe. No se ejecutaron pruebas funcionales por tratarse de una decisión documental.
- **Pendiente:** implementar despachador, worker y reconciliador; ensayar con PostgreSQL y Redis reales una caída abrupta, un aviso perdido, avisos duplicados y un lease vencido. Esas pruebas validarán o forzarán a ajustar los plazos antes de cerrar el corte.
