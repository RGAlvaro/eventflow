### P-11 — Receptor controlado de demostración

**Opción elegida.** El receptor es un proceso independiente de EventFlow en un host externo dedicado a **una sola organización de demo**. Un proxy publica su nombre DNS público con certificado válido en HTTPS/443 y reenvía a un puerto local del proceso; el backend registra únicamente esas URL HTTPS. El proxy limita el cuerpo a 256 KiB y no registra cabeceras de autorización ni cuerpos. El proveedor, dominio concreto y certificado se elegirán en P-08 antes de exponerlo. No se añade una excepción SSRF: la salida de EventFlow resuelve y fija una IP pública en cada intento como cualquier otro webhook. No existe ruta pública para cambiar escenarios, secretos ni destinos.

Cada ruta `/hooks/<escenario>` pertenece a un endpoint de EventFlow y tiene un secreto independiente de 32 bytes, recibido una sola vez al crear ese endpoint y copiado mediante canal seguro en el mismo base64 URL-safe a un archivo local del receptor legible solo por su usuario. El archivo se monta fuera del repositorio y contiene versiones de secreto por `X-EventFlow-Key-Id`; durante una rotación puede aceptar versión antigua hasta `not_after` y después se retira. Un token aleatorio distinto protege `/observations/<escenario>/<delivery_id>`; solo el backend de la demo lo usará, nunca el navegador. El receptor comprueba HMAC sobre los bytes exactos, timestamp ±300 segundos y coincidencia de IDs/generación del cuerpo y cabeceras antes de modificar su registro. SQLite local conserva únicamente IDs, generación, número de peticiones, último código, hora y marca de procesado; no conserva payload, secreto, firma ni cuerpo de respuesta. Su transacción serializa duplicados concurrentes y exige directorio `0700` y archivo `0600`. Las copias de SQLite y del archivo de secretos se tratan por separado en P-08.

Los cuatro modos preconfigurados son `success` (200), `transient` (503 dos veces, luego 200), `rate_limit` (429 con `Retry-After: 2`, luego 200) y `fail_until_replay` (503 en la generación inicial 1; 200 desde la generación 2). Una petición duplicada después del primer 200 responde 200 sin nuevo procesado. La UI futura elegirá entre destinos ya creados y mostrará el estado real de EventFlow y la observación sanitizada del receptor a través del backend autorizado por organización. El modo de replay permite repetir el recorrido sin una ruta administrativa pública que cambie el estado del receptor.

**Alternativas y consecuencias.** Incrustar el receptor en el VPS de EventFlow abriría una ruta hacia una red interna o forzaría a relajar SSRF; D-17 ya fijó la separación externa. Configurar modos mediante una ruta pública necesitaría otro mecanismo de autorización y permitiría interferir en otras demos. SQLite es suficiente para este receptor de una sola organización y conserva deduplicación tras reinicio; no se usa como fuente de verdad de entregas de EventFlow, que sigue siendo PostgreSQL. Si el receptor pierde su disco, EventFlow puede volver a enviar físicamente y la deduplicación del receptor ya no está garantizada; P-08 definirá copia y restauración.

**Comprobación.** Las pruebas de P-11 cubren firma, manipulación, antigüedad, vencimiento de clave, 413, cuatro modos, concurrencia, reinicio, token de observación y envío desde un reclamo real del worker a un servidor HTTP local autorizado solo en test. La integración externa HTTPS con DNS y certificado reales queda para el smoke test de despliegue del hito 6; no se afirma que esté desplegada ahora.

### P-07 — Consultas paginadas

**Opción elegida.** Los listados se ordenan por tiempo de creación descendente y UUID descendente para resolver empates. Eventos aceptan filtro exacto de tipo; entregas, filtros exactos de evento y estado; intentos se consultan para una entrega concreta. Cada página contiene entre 1 y 100 elementos (25 por defecto) y un cursor opaco para continuar. El cursor incluye versión, posición, organización y filtros; se rechaza si su formato o contexto no coincide. Un cursor no concede acceso: cada consulta comprueba de nuevo la credencial `manage` y filtra por organización. Las respuestas de lista omiten payload y secretos; los detalles autorizados muestran el payload del evento y metadatos sanitizados de entrega e intento.

**Motivo y alternativa.** Un desplazamiento numérico cambia de significado cuando llegan eventos nuevos: un operador puede ver filas repetidas u omitirlas al pasar de página. Comparar el par `(fecha, UUID)` con la última fila mantiene una continuación estable para registros nuevos y evita recorrer todas las filas anteriores. El límite de 100 acota trabajo y tamaño de respuesta. Un cursor firmado no sustituiría la comprobación tenant en PostgreSQL; la vinculación del contexto sirve para detectar usos accidentales con filtros diferentes. Los datos eliminados por retención desaparecen naturalmente de páginas posteriores.

**Comprobación.** Pruebas con PostgreSQL real cubrirán empates de fecha, inserción entre páginas, límites, filtros, cursor inválido y tenant cruzado. Los índices siguen organización y orden de paginación. La sesión de navegador se decide en P-10; mientras tanto estas rutas exigen `manage` como las demás rutas de gestión.

### P-10 — Sesión del operador

**Opción elegida.** El comando de operador del servidor crea un usuario único para una organización y entrega una contraseña aleatoria una sola vez. Se guarda `scrypt` con sal individual; rotarla o deshabilitar el usuario invalida todas sus sesiones. El login limita tanto el total de intentos compartidos (ráfaga 10, reposición 2/s) como los de cada nombre de usuario (ráfaga 5, uno cada 12 s) con buckets atómicos de Redis. El límite global impide eludir la protección probando nombres distintos. Si Redis no está disponible, el login falla cerrado; usuario o contraseña incorrectos reciben el mismo error. El navegador recibe una cookie de sesión aleatoria, opaca, `HttpOnly`, `SameSite=Strict`, con `Secure` en producción y duración absoluta de ocho horas. PostgreSQL guarda solo el hash de ese token, su organización, usuario, expiración y revocación; cada petición comprueba esos datos. Un login nuevo invalida la sesión anterior del mismo operador. No se guarda ninguna clave API en el navegador ni en la sesión.

Las lecturas de gestión aceptan esa sesión. Toda mutación de gestión realizada con cookie exige una segunda cookie CSRF legible para la aplicación y el mismo valor en `X-CSRF-Token`; PostgreSQL guarda su hash ligado a la sesión. Una petición con cabecera `Authorization` sigue usando exclusivamente la clave `manage` y nunca cae de forma silenciosa a la cookie. El logout revoca la sesión. Las auditorías de gestión y replay distinguen el ID del operador del ID de una clave API, siempre con el tenant verificado. En desarrollo aislado se admiten cookies sin `Secure` sobre HTTP local; producción usa HTTPS y cookies `Secure`.

**Alternativas.** Un JWT autocontenido evita leer PostgreSQL por petición, pero complica revocación inmediata y el vínculo de auditoría en este MVP. Guardar una clave `manage` en `localStorage`, `sessionStorage` o el bundle la expone al JavaScript y a extensiones; por ello se usa una credencial distinta. Un enlace temporal no fue la preferencia del propietario (D-16). La contraseña se administra desde el servidor, no por una ruta pública de alta.

**Comprobación.** PostgreSQL/Redis reales y un cliente HTTP con cookies probarán login válido e inválido, límite individual y global con nombres distintos, falta de Redis, expiración, reemplazo, rotación/revocación, CSRF ausente o erróneo, lectura y mutación tenant, auditoría y que la clave API no aparece en respuestas/cookies. La sesión no sustituye la política del proxy del VPS prevista en P-08.

### P-05 — Secretos de firma y cifrado

**Opción elegida.** Cada endpoint recibe un secreto de firma independiente de 32 bytes generado con un generador criptográfico; la API lo muestra una sola vez al actor de gestión autorizado. En PostgreSQL se conserva únicamente cifrado con AES-256-GCM mediante una biblioteca mantenida: nonce aleatorio nuevo de 96 bits por cifrado, identificador de la clave de cifrado, versión del secreto y texto cifrado con etiqueta de autenticidad. Los bytes asociados autenticados incluyen `organization_id`, `endpoint_id` y versión, para detectar que una fila cifrada se copió a otro endpoint o versión. La clave maestra de cifrado es distinta de los secretos HMAC de los endpoints, distinta en test/desarrollo/producción y se entrega al proceso fuera de Git y de la base de datos. Solo los procesos que crean o usan secretos la reciben; no se registra ni se devuelve en consultas. El worker descifra antes de consumir un intento; una clave ausente o una autenticación fallida impiden el envío y producen una condición operativa visible, sin marcar la entrega como éxito, agotar el presupuesto de reintentos ni perder su trabajo recuperable.

La rotación del **secreto de firma** crea una versión nueva para que el receptor pueda instalarla antes de activarla. Al activar, las firmas nuevas llevan `X-EventFlow-Key-Id` con la versión pública y usan el secreto nuevo; los envíos ya iniciados pueden llegar con la versión anterior. El receptor de ejemplo acepta ambas versiones durante una ventana de 24 horas desde la activación y luego descarta la anterior; EventFlow deja de usarla para intentos nuevos inmediatamente. La gestión de versiones y la activación requieren credencial `manage` del mismo tenant y dejan auditoría sin material secreto. Si se sospecha compromiso, se permite activación inmediata y revocación de la versión antigua sin esperar la ventana, aceptando que un envío ya iniciado pueda fallar. La versión antigua cifrada se elimina al acabar la ventana; nunca se reutiliza su identificador.

La rotación de la **clave maestra** sigue el orden: instalar clave nueva junto a la antigua, escribir solo con la nueva, volver a cifrar cada secreto conservando su identidad y versión, verificar que no quedan filas con el identificador antiguo, y solo entonces retirar la clave antigua. El descifrado escoge la clave por el identificador guardado. Se ensaya el proceso con una copia restaurada antes de retirar una clave en producción. Un backup de PostgreSQL sin sus claves maestras no recupera los secretos; la copia cifrada de las claves se custodia y restaura por separado según P-08. Si se pierde irrecuperablemente una clave, se desactivan los endpoints afectados, se avisa al operador y se generan secretos nuevos tras reaprovisionar los receptores; no se intenta descifrar con otra clave ni enviar sin firma. La pérdida de la clave no se trata como un fallo transitorio que agota silenciosamente los siete intentos.

**Alternativas descartadas.** Guardar el secreto en claro o usar solo cifrado del disco deja el secreto legible en un volcado de PostgreSQL. Usar una única clave para todos los entornos permite que una filtración alcance la demo y producción a la vez. Sustituir el secreto activo sin versión ni ventana impide al receptor distinguir firmas emitidas durante la transición. El cifrado por endpoint con una clave maestra local evita exigir un servicio externo de gestión de claves para el MVP de un VPS; P-08 fijará el mecanismo concreto de entrega y backup de esa clave.

**Consecuencia y comprobación.** EF-01, EF-04 y EF-10 exigirán pruebas de cifrado y datos asociados, nonce distinto para el mismo secreto, lectura con clave equivocada, separación de entornos, rotación en presencia de entregas y retirada de clave maestra solo tras recifrar. También se probarán redacción de API/logs y recuperación de una copia. Hoy `Endpoint.signing_secret_ciphertext` contiene bytes de fixture usados directamente al firmar: el nombre de la columna no constituye cifrado. Esta decisión es un diseño cotejado con la [guía de secretos de OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html), la [guía de almacenamiento criptográfico de OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Cryptographic_Storage_Cheat_Sheet.html) y la [documentación de AESGCM de cryptography](https://cryptography.io/en/latest/hazmat/primitives/aead/); aún no demuestra implementación ni recuperación real.

### P-06 — Admisión, autorización y retención

**Opción elegida para ingesta.** Tras autenticar la clave `publish` y antes de crear un evento, un token bucket por `organization_id` admite inicialmente 10 peticiones por segundo con ráfaga de 20. Redis ejecuta en una operación atómica la lectura, reposición y consumo del bucket, usando su propio reloj y caducidad de claves inactivas; dos instancias API no pueden conceder el mismo token. Se cuentan también las repeticiones con `Idempotency-Key`: cada petición consume capacidad HTTP aunque devuelva el ID anterior. Al agotarse el bucket se responde `429` con código estable `ingest_rate_limited` y `Retry-After` en segundos, calculado hasta el siguiente token y redondeado hacia arriba. Ningún `429` crea un evento ni un outbox. Redis no conserva el trabajo aceptado: si está indisponible o el limitador no puede decidir, se responde `503` con `Retry-After: 5` antes de la transacción de ingesta. La cuota es por organización, no por clave, IP ni instancia.

Para impedir crecimiento sin cota, el MVP admite inicialmente hasta 20 endpoints, 100 suscripciones y 10 claves API activas por organización. La creación se comprueba de forma transaccional bajo concurrencia; al superar una cuota de configuración devuelve `409` con código `resource_quota_exceeded`. Se admiten además 1 000 eventos nuevos por organización y día UTC, contados en PostgreSQL mediante una reserva transaccional; al agotarse la cuota diaria se devuelve `429` con código `ingest_daily_quota_exceeded` y `Retry-After` hasta el siguiente día UTC. Se limita también a 10 000 entregas no terminales por organización: la admisión se comprueba en la misma transacción PostgreSQL que crea evento, entregas y outbox, de modo que dos publicaciones simultáneas no rebasen la capacidad. Si falta capacidad, la transacción se revierte y se devuelve `503` con código `ingest_capacity_exhausted` y `Retry-After: 5`. Una repetición idempotente de un evento ya aceptado devuelve su `202` previo aunque se alcance después la cuota diaria o la capacidad de entregas, pero sigue sujeta al límite de peticiones. Estas cifras son valores iniciales para probar y ajustar con la carga del hito 5, antes de la exposición pública.

El cuerpo HTTP completo de `POST /api/v1/events` conserva el máximo de 256 KiB ya aplicado por la API, contado en bytes de entrada, sin depender de `Content-Length`; se configura el mismo máximo o uno más estricto en el proxy del VPS. Exceso: `413` con `body_too_large`, sin inserción. Se limita el tamaño antes de parsear JSON; la API y el proxy deben cortar la lectura al superar el máximo. Los límites de salida y los plazos del worker siguen separados en P-09/P-04.

**Autorización.** `publish` solo permite publicar. `manage` de la organización puede administrar claves, endpoints y suscripciones y solicitar replay de una entrega `dead_lettered` de esa misma organización; ni una clave `publish`, ni una `manage` revocada, ni una credencial de otro tenant pueden hacerlo. El ID de entrega aportado nunca determina el tenant. Replay conserva auditoría de `actor_key_id` y generación. La sesión del navegador prevista en P-10 deberá representar ese alcance sin poner la credencial bruta en el cliente. Las operaciones de configuración y replay requieren pruebas con las tres clases de credencial y con IDs cruzados.

**Retención.** Se conservan evento, payload, entregas, intentos, outbox y auditoría de replay durante 30 días contados desde que **todas** las entregas del evento quedan en estado terminal (`succeeded` o `dead_lettered`); un evento sin entregas es terminal al crearse. Mientras haya trabajo pendiente, en reintento o con lease, no se elimina ninguna pieza necesaria para recuperarlo. Una solicitud de replay dentro del plazo vuelve a abrir la entrega y reinicia el reloj de retención del conjunto cuando vuelve a quedar terminal. La purga periódica elimina el conjunto en una transacción con bloqueo/condición de estado, por tenant, sin dejar referencias huérfanas; tras la purga, la misma `Idempotency-Key` puede crear un evento nuevo, por lo que el productor no debe asumir deduplicación indefinida. Las claves API revocadas se conservan como identidad de auditoría mientras exista una auditoría que las referencie. Las copias de seguridad mantienen su propio plazo, fijado en P-08, y no se consideran purgadas al borrar la fila activa.

**Alternativas descartadas.** Un límite local en cada API permite exceder la cuota al añadir réplicas. Usar solo una IP mezcla tenants detrás de un proxy. Aceptar eventos cuando el limitador no responde crea un camino sin límite en la condición de fallo. Borrar registros por edad de creación puede eliminar una entrega aún pendiente o invalidar un replay. Guardar idempotencia indefinidamente impide una retención acotada sin una tabla separada de claves históricas.

**Consecuencia y comprobación.** EF-01 a EF-03, EF-07 y EF-10 requieren pruebas concurrentes del bucket, el cambio de día UTC y las cuotas, `429`/`503`/`413` sin `202` ni trabajo parcial, fallo de Redis antes de ingesta, replay cruzado y revocado, y purga con entrega pendiente, terminal y reabierta. Un ensayo de carga medirá tasa admitida, latencia, backlog y memoria; si los valores iniciales no sostienen el VPS elegido, se ajustarán con evidencia antes de exposición pública. Hoy solo existe el límite API de 256 KiB y replay interno con `manage`; no existen bucket, cuotas ni purga. La elección del bucket atómico se cotejó con la [documentación de limitación de Redis](https://redis.io/docs/latest/develop/use-cases/rate-limiter/) y la [guía de denegación de servicio de OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Denial_of_Service_Cheat_Sheet.html). Esta revisión documental no sustituye esas pruebas.

### P-03 — Destinos HTTP seguros

**Opción elegida.** En producción, aceptar solo URL HTTPS con nombre DNS público y puerto 443 (explícito o implícito). El host debe ser un nombre DNS normalizado con al menos dos etiquetas; se rechazan IP literal, credenciales en la URL, fragmento, host con codificación ambigua y cualquier otro esquema o puerto. Conservar ruta y consulta solo después de analizar y validar la URL completa con un único parser. HTTP hacia el receptor local requiere una configuración explícita exclusiva de tests o desarrollo aislado, imposible de activar en producción.

En **cada intento** de envío, resolver A y AAAA, rechazar el destino si la resolución falla o devuelve cualquier dirección no pública (incluidas direcciones privadas, locales, de enlace, reservadas o IPv4 embebidas en IPv6), y elegir únicamente una IP validada. Si se prueba otra IP, también debe pertenecer al conjunto validado para ese intento; un nuevo intento vuelve a resolver y comprobar. Construir la petición HTTPX para esa IP, fijar la cabecera `Host` y la extensión `sni_hostname` al nombre DNS original, mantener verificación TLS y usar HTTP/1.1. Así, la conexión TCP usa la IP comprobada mientras el servidor recibe el nombre correcto y el certificado se comprueba contra ese nombre. Desactivar seguimiento de redirecciones y proxies de entorno (`follow_redirects=False`, `trust_env=False`); no reenviar automáticamente una respuesta 3xx. Un error de DNS, validación o TLS falla cerrado y no genera conexión a un destino alternativo sin comprobar.

En el VPS, limitar además la salida del proceso de envío: permitir solo las IP y puertos internos indispensables para PostgreSQL, Redis y DNS según su función, y el tráfico HTTPS a direcciones públicas; bloquear el resto de redes internas y metadatos del proveedor mediante reglas efectivas para contenedores, verificadas en P-08. Esta barrera de red complementa la comprobación de la aplicación; la configuración exacta depende de la topología medida del VPS.

**Alternativas descartadas.** Validar solo al registrar el endpoint, o resolver antes del envío y dejar que HTTPX vuelva a resolver el dominio, permite un cambio de respuesta DNS entre validación y conexión. Una lista de dominios permitidos tampoco evita por sí sola ese cambio. Aceptar solo destinos preconfigurados sigue siendo la alternativa de alcance si no se demuestra la conexión fijada a IP; no habilita URLs arbitrarias. HTTP público o puertos adicionales amplían la superficie de salida sin ser necesarios para el primer corte.

**Consecuencia y evidencia.** El primer corte no admite destinos HTTPS por IP ni puertos distintos de 443. Se revisó el contrato de `docs/architecture.md`, la [guía SSRF de OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html) y la [extensión `sni_hostname` de httpcore](https://github.com/encode/httpcore/blob/master/docs/extensions.md); estas fuentes respaldaron el diseño. Las pruebas locales del hito 1 verificaron resolución mixta con IP no pública, IPv4/IPv6 internas, URL ambigua, petición construida con IP fijada/Host/SNI, redirecciones y proxy desactivados, conexión TLS a la IP elegida y rechazo de certificado para otro nombre. La conexión fijada evita una segunda resolución del dominio durante el envío. Las reglas de salida del VPS se comprobarán antes de exponer la demo.
